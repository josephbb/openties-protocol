# Author disclosure protocol 0.3

The three JSON Schemas define the wire objects. The rules below define their meaning. Implementations must validate structure, formats, identifiers and dates before evaluation. Invalid or unsupported input is an error. A valid policy with insufficient evidence yields an indeterminate answer.

## Policy and versions

The policy carries a globally unique publisher-controlled policyId, an opaque revision, publisher name, human-readable title, policy URL, role, named vocabulary and ordered rules. Use a publisher-controlled HTTPS identifier in production. Both parties must agree on the authoritative publisher and policy content. Labels and question wording are plain text. The URL provides the human policy and provenance. Evaluators use the pinned policy content and the reviewed input snapshot. Evaluation performs no live registry lookup.

Each rule, organization and relationship type has a unique ID within its respective list. Every rule reference must resolve. Policy authors spell out which named legal entities a rule covers, including any subsidiaries, and define each organization type in the policy. They explain each relationship type in the associated human policy. IDs must retain their meaning. The binding to a policy revision includes its human definitions. Archive the versioned human policy alongside the serialized rules. If a clause needs individual judgment, include an author question. A policy may be represented as a whole only when every required clause is represented.

Protocol version is an exact string. Implementations must reject unsupported versions and unknown rule kinds or fields. A change to the meaning of a date, rule, outcome, or wire object requires a new protocol version. Editorial clarifications that leave all valid inputs and outputs unchanged can be issued as documentation errata. The reference package has a separate software version. Behavior-changing fixes must identify affected protocol versions and conformance cases.

A publisher must issue a new immutable policy revision for changes to rules, membership, definitions, question wording, or windows. A receipt refers to the exact protocol, policy and revision used. Replaying it requires the original submission date and authorized input snapshot. A later policy cannot replace those inputs.

### Moving from 0.1

Draft 0.2 changes identity validation, adds type selectors and rejects contradictory claims about future support. Keep the 0.1 evaluator and pinned inputs for replay of older receipts. A new evaluation under 0.2 requires remapping old out-of-list IDs and reviewing the affected rules. Changing a policy to include a whole sector also requires a new policy revision. A previously complete review of two named companies supplies no assurance about all companies.

### Moving from 0.2

Draft 0.3 adds explicit unrestricted selectors, relationship categories and reviewed additional relationship types. Keep the pinned 0.2 implementation for earlier submissions. Issue a new policy revision and collect a fresh attestation when broadening a rule. Checking every organization on an earlier list does not establish coverage of every organization the author dealt with.

## Inputs and meaning of a rule

The evaluation is for one author and one submission. submissionId is an opaque, recipient-scoped identifier for that author's submission. submissionDate is the calendar date of submission, independent of the day the evaluation runs. The authenticated host binds the author, journal, submission, policy revision and date.

- A ties rule requires a relationship match, an organization match and a time or work match. Each selector dimension must be explicit. Empty lists are invalid. The same evaluation supplies both receipt modes. An adapter may omit a tie only when it has established that the tie is irrelevant to every tie rule. Preserve uncertainty as null or an unresolved rule. Open evidence requires confirmation.
- A lookback window includes both endpoints. Subtract the given number of calendar months from submissionDate and clamp the day to the last day of the target month. A tie qualifies if its interval intersects this window.
- A submitted-work rule covers direct support for this particular work by submission, regardless of when it began. The input's supportedSubmittedWork is a submission-specific determination. An older grant may qualify. If the earliest feasible start is after submission, affirmative support is contradictory input and must be rejected. For a future tie with a false or unknown answer the work criterion is false. A same-year start with unknown day can be consistent with confirmed support. If a commitment itself supported the work, the author must confirm that fact and record when the commitment began.
- An author-question is phrased so that yes reports an interest, no clears that question, and absent or null leaves it unanswered. A question can ask about a personal, professional or perceived interest that the structured ties do not capture. Multiple answers to one question are invalid.
- completeRuleIds records the author's explicit attestation that all relevant ties for each listed tie rule, including its relevant period or work, are represented in this snapshot. unresolvedRuleIds identifies tie rules affected by outstanding evidence or unresolved coverage. Only tie rules may appear in either list. Missing answers, pending records, reduced source scopes and year-only data must survive adaptation. The host must invalidate or reconfirm affected attestations after material changes.

Dates on ties are exact days, calendar years, or null. A year ranges from January 1 through December 31 inclusive. A null endpoint is unknown. Consider all feasible start and end dates consistent with the supplied values and start ≤ end. If all feasible intervals overlap the window, the time criterion is true. If none overlap, it is false. Otherwise it is indeterminate. An impossible interval is an input error. An ongoing tie can use its known active-through date for an evaluation anchored on that date. For other anchors the adapter must retain uncertainty about its end when material.

## Relationship types and categories

A rule with `anyRelationship: true` covers every confirmed relationship. Otherwise it selects one or more `relationshipTypes`, `relationshipCategoryIds`, or both. A category in the policy’s `relationshipCategories` has a unique ID, a label, and a nonempty list of relationship type IDs from the policy vocabulary. Expand selected categories to their pinned member types and take the union with explicitly selected types. Overlapping categories produce one match per returned relationship and organization within a rule. A wildcard and a narrower selector on the same dimension are invalid together.

A non-null relationship type in a tie must resolve to a policy term or a reviewed term in the input’s `additionalRelationshipTypes`. Each additional term carries a stable, shareable ID, a private display label and `distinctFromListed: true`. The adapter must establish that it falls outside all of the policy’s defined relationship types before making that assertion. If classification remains ambiguous, use null. A wildcard can cover a confirmed tie even when its precise type is unknown. Only the type ID or null is eligible for inclusion in a receipt.

## Organization identity and types

1. Each named or additional organization with a verified ROR record must use its full lowercase `https://ror.org/<id>` as the canonical ID. The adapter verifies the record for the exact entity before pinning it. The evaluator validates the ROR identifier pattern and checksum offline. For organizations without a verified ROR record, use a stable alternative identifier only after resolving the identity. [ROR identifier specification](https://ror.readme.io/docs/identifier) A named organization’s optional `externalIds` lists verified non-ROR HTTPS identifiers for that entity. ROR references on ties and type answers accept the nine-character token, the `ror:` prefix, or the ror.org URL (optional HTTP/HTTPS scheme, www prefix, and trailing slash). Normalize these references case-insensitively to the full lowercase ROR URL and validate the leading zero, six Crockford base-32 digits and two decimal checksum digits per the registry specification. Compare other identifiers exactly. An alias must be unique across all canonical IDs and aliases. Rule selectors always use canonical policy IDs.
2. A tie or type answer may reference a named organization by canonical ID or pinned alias. An identified organization absent from that list must have a private `additionalOrganizations` entry with a stable shareable ID, label and `distinctFromListed: true`. The adapter must have verified that it is distinct from every listed entity. Preserve an unresolved tie identity as null. An undeclared non-null ID is an input error. The host must never derive a distinctness assertion solely from a failed name or registry lookup.
3. A policy may declare `organizationTypes`, each with an ID, label and definition. `organizationTypeAnswers` records one reviewed boolean per organization and policy type for this submission. A missing answer means unknown. An organization may satisfy several types. Duplicate answers, including through aliases, and unknown references are invalid. The host keeps the supporting evidence and interpretation with the snapshot. A negative classification requires affirmative evidence under the definition.
4. A rule with `anyOrganization: true` covers any organization and requires no classification by sector or name. Otherwise it specifies at least one nonempty selector, `organizationIds` or `organizationTypeIds`. Combining the wildcard with either narrower selector is invalid. Within and across the lists the operation is **OR**. An exact named match wins. Otherwise any confirmed type match suffices, including for additional organizations. With no match, any unresolved selected type or unknown identity leaves the organization criterion indeterminate. When all selected criteria are known false it is false. Another independently false rule predicate can still exclude the tie.
5. A confirmed tie match includes the canonical organization ID when known. For a type-based match it also includes `organizationTypeId`, the first confirmed type in rule order. Named and unrestricted organization matches omit that field. Only one match per rule, relationship and organization is returned. The private label for an additional organization can be used in the manuscript statement. Only the approved ID appears as its identity in the receipt.

## Evaluation and disclosure

A confirmed tie matches when all the rule predicates are true. One false predicate rules it out. A remaining unknown makes it a possible match. For each ties rule, completeness requires explicit attestation, no possible matches left unresolved, and no outstanding evidence identified for the rule. A definite match yields true even if coverage is incomplete. With no definite match the rule yields false only when complete, otherwise null. A question is complete once answered yes or no.

A confirmed organizational tie can settle the overall answer even if the author cannot identify the exact organization or relationship type. An unrestricted selector is true for that dimension. A narrower selector with an unresolved detail is indeterminate. If every predicate is true, emit the match with any unknown detail explicitly null and mark the rule incomplete until those details are resolved. For example, confirmed funding in 2024 from an unidentified organization establishes funding from *some* organization during a five-year window ending in 2026. It cannot establish funding from a charity. An unconfirmed suggestion supplies no such match.

Across rules, any true gives true. With all false the result is false. Otherwise it is null. Completeness is tracked independently and requires every rule to be complete. Reportable means at least one interest must be disclosed under this policy. Editorial handling is a separate decision.

An author-facing statement must draw its claims from the same evaluation. It may name confirmed matches. A negative or “no other” declaration requires complete coverage and must identify the policy scope. If incomplete, show that the assessment is incomplete. Specific presentation and language may vary. See the expected English renderings in the examples.

The host must show the recipient and exact release to the author before issuing a receipt. Default flag mode reveals only the result and binding metadata. In matches mode include the confirmed tie matches defined above or the question rule ID for an affirmative answer. Within a rule, collapse identical returned items. Preserve first input occurrence and policy rule order in the reference serialization. A true result can have further unresolved questions. A receipt omits completeness diagnostics, pending evidence, private identifiers, notes, amounts and unapproved free text. The author may give context to the editor separately.

Each receipt has a fresh receiptId. To correct it, issue a newly approved receipt with supersedes pointing to the previous receipt for the same author, recipient and submission. The original remains identifiable. Hosts must validate ownership, recipient, lineage and the active predecessor before accepting a correction. A receipt is a data format. Delivery, identity, authentication, signatures, retention and withdrawal are host responsibilities.
